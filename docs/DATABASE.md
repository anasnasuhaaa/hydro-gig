# PostgreSQL, Neon, and PostGIS

The schema is prepared; no database is needed to start either application. All primary keys are application-generated UUIDs. All tables have timezone-aware `created_at` and `updated_at`. SQLAlchemy maintains `updated_at` on ORM writes; direct SQL writers must do so explicitly.

| Table | Purpose and relationships | Spatial data |
| --- | --- | --- |
| `drivers` | Minimal display identity; trips and optional observations link to driver | None |
| `road_segments` | Unique source reference and positive length in meters | LINESTRING, SRID 4326 |
| `flood_scenarios` | Explicit provenance, source, JSONB manifest for parameters/model/dataset versions | None |
| `flood_observations` | Optional scenario, road segment, driver; required time, provenance, source; nullable nonnegative depth in meters | POINT, SRID 4326 |
| `trips` | Required driver; planned/active/completed/cancelled status; consistent optional start/end times | Origin/destination POINTs, SRID 4326 |
| `claims` | Required trip, optional observation; draft/submitted/reviewed status; description; nullable unique future digest | None |

Foreign keys use RESTRICT to preserve linked evidence. Spatial columns receive GiST indexes through GeoAlchemy2 DDL. Foreign keys and observation time are indexed. WGS84 uses longitude, latitude order; degrees are not meters. Compute distances with an appropriate projected CRS or geography rather than raw 4326 geometry length.

Observation/scenario provenance accepts `observed`, `simulated`, or `model_predicted`. Derived observations require a scenario. The manifest must eventually identify units, parameter sources, model version, and uncertainty. No rows or constants are seeded. A nullable digest is a schema reservation, not token generation. Future services must enforce scenario/observation consistency and evidence chain-of-custody.

## Manual database preparation

1. Create a Neon project and separate development/preview/production branches as needed.
2. Enable PostGIS through an authorized SQL console on the intended database:

   ```sql
   CREATE EXTENSION IF NOT EXISTS postgis;
   SELECT PostGIS_Version();
   ```

3. Set backend `DATABASE_URL` to Neon's pooled runtime URL and `DIRECT_DATABASE_URL` to the direct migration URL. Preserve `sslmode=require` and other security options supplied by Neon. `postgresql://` and `postgresql+psycopg://` normalize to psycopg 3. Runtime uses NullPool; migrations prefer the direct URL.
4. Review and run migrations manually:

   ```bash
   cd backend
   source .venv/bin/activate
   alembic upgrade head
   alembic current
   ```

PostGIS is an administrative prerequisite; the migration does not create or remove it. Startup never migrates. Missing credentials yield `not_configured`.

## Migration workflow

`alembic/versions/0001_foundation.py` is an immutable schema snapshot independent of future model edits. Review future autogenerated revisions for spatial indexes and extension-owned tables. On a development database:

```bash
alembic revision --autogenerate -m "describe change"
alembic upgrade head
alembic check
```

For offline SQL review, supply a syntactically valid PostgreSQL URL and run `alembic upgrade head --sql`; this opens no connection. Only use `alembic downgrade base` on an explicitly disposable database: it drops application tables and their data. No live downgrade was performed during foundation work.

PostgreSQL DDL compilation and offline migration SQL can be checked without credentials. A live upgrade/downgrade cycle and drift check remain required on a manually provisioned PostGIS development database.
